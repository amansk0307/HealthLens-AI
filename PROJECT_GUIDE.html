01 / Start here

The project in one minute

HealthLens is a single-process Streamlit app. It brings together educational prediction demonstrations and a source-grounded chatbot and tutor. The UI and page orchestration live in one large script; reusable logic for symptom ranking, image inference, retrieval, Groq, and tutoring lives in code/.

1main UI entry point: app.py
7active Python helper / training modules
32curated local chatbot knowledge entries
4focused automated test modules
UI

The interface

Sidebar navigation chooses a page. Streamlit reruns app.py as users interact; page blocks show forms, images, chat, and results.

ML

The prediction demos

Inputs go to saved classifiers or, for liver prediction, a decision tree fitted from a local CSV during the page run.

RAG

The source-grounded assistant

Questions are matched to local reviewed passages. The chatbot may ask Groq to word a response using those passages; some safety-sensitive replies are composed locally.

3×

The learning tutor

A three-step plan, short lessons, and answer checks are composed from reviewed passages and tracked in the current Streamlit session.

Important boundary. App output is educational demonstration output—not a diagnosis, calibrated medical probability, or treatment plan. Do not enter real names, identifiers, or personal health information into the Groq-backed features.
02 / How the app starts

Architecture & request flow

The menu is the routing mechanism. There is no separate API server, database, or front-end bundle in the active app.

1

Configure. app.py imports packages, reads the favicon, sets Streamlit page config, and injects global CSS.

2

Route. The sidebar menu sets selected; the matching conditional page block renders.

3

Collect. Widgets capture symptoms, measurements, images, chat text, or tutor answers.

4

Compute. The page calls a model/helper, retrieval module, or tutor service. Streamlit reruns the script on interactions.

5

Show. Results are rendered in the same page. Chat and tutor progress live in st.session_state, not durable storage.

Rerun detail: any top-level statement outside a page-specific conditional also runs again on interaction. In particular, Diabetes and Parkinson model deserialization is currently at module scope.
03 / Interactive pages

Prediction pages: input to result

Symptom-based ranking

Choose symptomsoptions come from dataset columns
→
Encode featuresone-row binary array
→
XGBoostthree top class scores
→
Rank & explainlabels + dataset lookups

app.py creates DiseaseModel, loads models/xgboost_model.json, and offers all_symptoms. prepare_symptoms_array() maps chosen symptom names to a fixed-size vector using data/clean_dataset.tsv. DiseaseModel.predict_top_k() calls XGBoost predict_proba, then rank_disease_probabilities() maps model classes to the ordered disease labels. The UI shows three matches, descriptions from symptom_Description.csv, and optional precaution text from symptom_precaution.csv.

The displayed scores are ranking scores, not calibrated clinical probabilities. Empty symptom selection is stopped with a warning.

04 / Image inference

Image classifiers

MALARIA

Cell image

Upload JPG/PNG → resize to 224 × 224 → array shape [1,224,224,3], scale by 1/255 → load CNN_Model.h5 → threshold first output at 0.5 → infected / not infected message.

When it runs: model loads on upload; inference waits for Predict. Assumes three color channels.

PNEUMONIA

Chest X-ray

Upload JPG/JPEG/PNG → RGB → resize 224 × 224 → scale by 1/255 → load pneumonia_classifiers.h5 → call predict → threshold first output at 0.5.

When it runs: prediction occurs on upload. A checkbox changes the preview, not the inference.

ALZHEIMER MRI

MRI category

Upload → convert RGB → cached model load → resize 244 × 244 → MobileNetV2 preprocessing → predicted class and score.

Model builder: code/alzheimer.py constructs a DenseNet201 backbone with pooling and dense layers and loads alzheimer_model.h5 weights.

Alzheimer inference call chain

app.py: upload + image validation
  └─ get_alzheimer_model()              [@st.cache_resource]
       └─ code.alzheimer.load_alzheimer_model()
            ├─ build DenseNet201 inference graph
            └─ load models/alzheimer_model.h5 weights
  └─ code.alzheimer.predict_alzheimer_image(image, model)
       ├─ RGB + resize + MobileNetV2 preprocessing
       └─ model.predict -> argmax -> four class names + score

The class names are Mild Demented, Moderate Demented, Non Demented, and Very MildDemented. The helper uses nearest-neighbor resizing. Confirm that this preprocessing matches how the weights were trained: the helper builds DenseNet201 but uses MobileNetV2 preprocessing.

Model files do not certify clinical performance. This guide describes the checked-in inference paths. It does not validate training data, calibration, external performance, or fitness for clinical use. Confirm each model’s channel layout, output semantics, and preprocessing against its training pipeline.
05 / Conversational AI

Vitalis AI: local references, optional generation

Search happens locally over the reviewed JSON knowledge base. Groq generates language only for the general-answer branch using the retrieved passages and safety instructions.

  1. build_retrieval_query() adds the latest user question only when the new message looks like a follow-up.
  2. retrieve_passages() loads the local index once, filters topic mismatches, and returns passages with source IDs.
  3. High-blood-sugar action questions use build_high_blood_sugar_guidance(); memory-loss concern questions use build_memory_loss_information().
  4. No relevant passages means the app declines to guess. Otherwise, context and chat history are passed through stream_groq_response().
  5. The UI streams text, normalizes generated text, shows sources with links/review dates, and stores turns in st.session_state.chat_messages.
API key. get_groq_api_key() checks Streamlit secrets, then the GROQ_API_KEY environment variable. Missing keys and request/response errors are surfaced in the UI. Messages are sent to Groq; do not enter identifying or personal health information.
06 / Learning journey

Health Literacy Tutor: a three-step loop

Pick a topicone of seven supported areas
→
Build planexactly three steps
→
Learn + checklesson and open question
→
Feedbackmastery, retry, XP, streak

health_tutor.py validates that a plan has exactly three non-empty title/objective pairs, maps lesson citations to local passages, requests an adaptive lesson, and checks answers as structured JSON. It never trusts model-generated source IDs for citations.

Mastered

+25 XP, streak increments, step advances, mastery count increments, and the next lesson can become slightly more challenging.

Not mastered yet

Supportive feedback, no points lost, streak resets, attempt number increments, and the next lesson re-explains the objective.

State includes topic, passages, plan, step index, attempt number, lesson, feedback, mastery status, XP, streak, and completion flag. It exists in the current browser session only. Topics: Alzheimer's disease and memory, diabetes, heart disease, liver disease, malaria, Parkinson's disease, and pneumonia.

07 / Source map

What each Python file does

  • app.pyMain Streamlit application: theme, navigation, all page UI, input validation/rendering, helper calls, session state, and error messages.
  • code/__init__.pyMakes code importable as a Python package.
  • code/DiseaseModel.pyLoads the XGBoost model, exposes symptom and disease labels, predicts/ranks labels, and reads disease descriptions and precautions.
  • code/disease_ranking.pyValidates top-k and class/probability alignment, orders scores, and maps class IDs to disease names.
  • code/helper.pyMaps selected symptom names to the feature-column order in the TSV and creates the model input array.
  • code/alzheimer.pyDefines MRI class names/size, constructs the DenseNet201 graph, loads weights, preprocesses an image, and returns predicted label/score.
  • code/chatbot_rag.pyLoads and validates JSON references, builds cached TF-IDF vectors, retrieves topic-filtered passages, and prepares contexts/citations/special-case answers.
  • code/groq_client.pyCentral Groq HTTP client: request construction, timeout, normal and streaming completions, error handling, and text normalization.
  • code/health_tutor.pyDefines supported topics and prompt rules; retrieves tutor sources; creates and validates plans, lessons, and answer feedback.
  • code/train.pyManual symptom model-training script: preprocess raw dataset, write cleaned feature TSV, fit/evaluate XGBoost, save artifacts.

How the TF-IDF retrieval works

1

Read and validate the JSON records; each must include ID, title, text, and source name.

2

Build a cached scikit-learn TF-IDF index over title + text (English stop words, unigrams and bigrams, sublinear term frequency).

3

Vectorize the question and rank passages by cosine similarity; apply minimum relevance, topic matching, special-query requirements, and source diversity.

4

Return passage text and citation/source metadata. This is local lexical retrieval—not live web search.

Keep training artifacts aligned. The cleaned TSV determines feature columns and disease category order. When retraining, verify that TSV columns, the model’s classes, and the inference vector all refer to the same order.

What is in unused/?

Dependency note

requirements.txt pins several packages but leaves core dependencies such as NumPy, Streamlit, and TensorFlow unpinned. TensorFlow H5, pickle/joblib, and XGBoost model compatibility can depend on library versions.

11 / Use & maintain

Run it, test it, change it

Local run

python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
streamlit run app.py

Run from the repository root because several paths are relative. Configure GROQ_API_KEY in the environment or Streamlit secrets before using the chatbot or tutor. Never commit secrets.

Test

python -m unittest discover -s tests

The existing suite focuses on the extracted retrieval, Groq client, tutor service, and ranking functions. It does not comprehensively exercise the Streamlit pages or every saved model.

Retrain the symptom model

  1. Review data/dataset.csv and the intended symptom columns.
  2. Run python code/train.py from the repository root. It regenerates data/clean_dataset.tsv and saves the XGBoost JSON model (the script also writes a compressed joblib artifact).
  3. Verify training feature and label order against helper.py and DiseaseModel.py.
  4. Run tests and trace a known input through feature vector, model class, and displayed label.

Maintenance checklist

  • Relative paths require launching at the repository root.
  • Diabetes and Parkinson artifact deserialization runs at module import/rerun, even on unrelated pages.
  • The Liver decision tree trains inside the page script; confirm data split, feature ordering, and expected reproducibility.
  • Check image channel assumptions, resize/preprocessing parity, and model output meanings against training code.
  • Session state is temporary; the app has no user account, database, or durable tutor progress.
  • Make the educational/non-diagnostic boundary obvious whenever changing result language.
